Tourism Management System — Project Progress Briefing
1. Project Start — Planning & Setup

I started the project as a Tourism Management System using Java Spring Boot.

The main goal was to build a system that can manage:

Tourism clients
Tour packages
Bookings
Payments
Notifications
Alerts
Hotels
Transportation
Trekking and expedition packages
Email communication

I created the Spring Boot project using the package:

com.tarpa.tourism

and configured the project with Spring Boot, Java, PostgreSQL and JPA/Hibernate.

2. Database Setup

After creating the project, I configured the PostgreSQL database using pgAdmin.

I created the database structure and connected the Spring Boot application to PostgreSQL.

The project now uses entities and repositories to communicate with the database.

3. Authentication & Security

After the basic project setup, I implemented authentication.

I worked on:

Register
Login
User
Role
JWT
Spring Security
Password Encryption

The authentication flow became:

Register
   ↓
User + Role
   ↓
Password Encryption
   ↓
Login
   ↓
JWT Token
   ↓
Authenticated API Access

I also implemented JwtAuthenticationFilter, JwtService, UserService, RoleService, and Spring Security configuration.

During this stage I solved several issues including authentication, authorization and 403 Forbidden errors.

After Client Management, I created the Tour Package module.

8. Alert Module

Then I moved to the Alerts module.

The purpose of Alerts is different from basic notifications.

Alerts are designed to handle time-based tourism events.

For example:

Booking Confirmation
Arrival
Hotel Check-in
Hotel Check-out
Transportation
Domestic Flight
Tour Start
Tour Return
Trekking Start
Trekking Return
Peak Climbing
Mountain Expedition
Helicopter Tour
Departure
Airport Transfer

The Alert is connected to the Booking.

9. Email Integration

After the Alert and Notification modules were working, I integrated real email sending.

This was an important milestone.

The system can now:

Alert
   ↓
Notification
   ↓
Email Service
   ↓
Real Email

I tested it with a real email address and successfully received an email from the application.

I also added support for CC email.

So the system can send:

TO → Client
CC → Company/Staff

This makes the system more realistic for a tourism company.

10. Automatic Scheduling

After manually testing alerts and emails, I implemented automatic scheduling using Spring's scheduling functionality.

I added:

@EnableScheduling

and created the scheduler functionality.

The idea is:

Scheduled Alert
       ↓
Scheduler checks time
       ↓
Alert becomes due
       ↓
Notification generated/processed
       ↓
Email sent

This means the system doesn't always require someone to manually send every alert.
